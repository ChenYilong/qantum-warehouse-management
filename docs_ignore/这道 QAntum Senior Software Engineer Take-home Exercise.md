这道 QAntum Senior Software Engineer Take-home Exercise，表面上是让你开发一个小型 Web 应用，实际上考察的是：你能不能像一名 Senior Software Engineer 一样，从业务问题出发，设计合理的方案，使用 AI Coding Agent 高效实现，并对最终交付质量负责。

结合你在 Microsoft 的企业级软件开发经历、.NET/Azure 架构背景，以及目前的 Senior Software Engineer / Architect 职业目标，这道题最值得展示的不是代码量，而是你的业务判断、技术决策、工程质量和 AI Agent 使用能力。

## 二、逐项解释：每一部分主要考察什么？

1\. Business understanding — 业务理解

考察：产品思维

题目要求你先理解 Team Leader 的真实工作，而不是直接打开 IDE 写代码。

你需要回答：

- 用户在什么时候遇到问题？
- 目前为什么难以做决定？
- 缺少材料会导致什么后果？
- 你的应用能帮助用户采取什么行动？

高分表现： 把“库存不足”转化成明确的业务决策，例如哪些施工任务受影响、哪些可以继续、哪些必须等待补货。

低分表现： 做一个漂亮的库存 CRUD 页面，却没有解决施工负责人真正需要解决的问题。

2\. Slicing — 任务拆分与范围控制

考察：Senior 的判断力

题目明确说，只需要实现整个工作流程中的一个有用切片（first slice）。

例如，不要一口气实现完整的库存系统、采购系统、排班系统、权限系统和移动端同步。

你需要先提出后续迭代计划，再选择第一期功能。

高分表现： 第一版足够小，可以在规定时间内完成；但它能解决一个真实问题，而且后续扩展路径清楚。

3\. Specification & Agent guidance — 需求规格与 Agent 指导

考察：能否把模糊需求变成可执行任务

你要编写简洁的 Markdown 规格文档，至少包含：

- Functional requirements：系统要做什么。
- Acceptance criteria：什么情况下才算做对。
- Non-functional requirements：性能、安全性、可靠性等要求。
- Assumptions：你做了哪些假设。
- Exclusions：本次明确不做什么。

例如：

- 库存不足时，系统必须显示短缺数量。
- 库存数据缺失时，不得错误显示为“库存充足”。
- 未获批准的替代防火方案不得直接标记为合规。

关键点： 这些文档不仅给人看，也要能够指导 Coding Agent 生成代码，并用于验证生成结果。

4\. Technical design & architecture — 技术设计与架构

考察：架构能力和技术取舍

开发前先说明：

- 前端采用什么组件和页面结构？
- 数据模型如何设计？
- 数据从哪里来，如何流动？
- 是否需要数据库、身份验证、持久化？
- 未来如何接入 QAntum 现有 Web 和 Flutter 应用？
- 为什么选择这些技术？

当前技术栈包括 React、Node.js、Flutter、Next.js、Supabase 和 Vercel。

不要求所有技术都用上。选择适合当前切片的最小技术组合，比为了展示技术而堆砌组件更重要。

5\. Agentic coding — AI 编程能力

核心考察之一

题目明确要求在整个开发过程中使用 Coding Agents。

不只是让 Claude Code、Codex 或其他 Agent 一次性生成整个项目，而是要展示你如何：

- 给 Agent 提供业务背景和明确约束。
- 让 Agent 按规格实现功能。
- 检查它生成的代码、数据模型和测试。
- 发现错误后纠正或拒绝它的建议。
- 通过自动化测试和部署结果验证最终交付。

他们甚至要求提供你使用的 Agent 指令、上下文文件，以及你纠正 Agent 的具体案例。

他们想知道的是：AI 是否真正提高了你的开发效率，同时你是否仍然掌握代码的控制权。

6\. Engineering quality — 工程质量

考察：能否交付可运行的软件

他们不满足于本地运行成功的 Demo。

要求包括：

- GitHub 仓库。
- 公开访问的前端应用。
- 自动化测试。
- CI/CD 流水线。
- 云端部署成功的证据。
- README、本地运行和部署说明。

还要测试异常场景，而不只是正常流程。例如库存缺失、材料不足、数据加载失败和无效输入。

这部分考察的是完整的软件交付能力，而不只是写 React 组件的能力。

7\. Ownership & walkthrough — 技术所有权与面试答辩

考察：你是否真正理解自己的系统

最后的面试会要求你现场演示，并回答：

- 为什么选择这个功能？
- 为什么采用这套架构？
- 用户点击按钮后，代码执行了什么？
- 测试覆盖了哪些风险？
- CI/CD 如何工作？
- Agent 生成了什么，你又修改了什么？
- 下一期准备做什么，为什么？

你需要能够从 UI 一直追踪到数据模型、业务逻辑、测试和部署。

如果代码是 Agent 写的，但你解释不清楚，那么很难证明你具备 Senior 工程师的能力。

### 为什么这个切入点好？

1. 业务价值明确： 帮助负责人在开工前发现风险，而不是到了现场才发现缺料。
2. 边界容易控制： 第一版只需要展示计划需求、库存、短缺和受影响任务。
3. 容易演示： 可以现场展示材料充足、短缺、数据缺失三种情况。
4. 容易测试： 库存计算、状态判断、异常数据都可以编写确定性的自动化测试。
5. 后续扩展自然： 补货、供应商交期、施工排期、替代方案审批等都可以作为后续迭代。

需要特别注意：题目没有提供真实的材料需求量、库存余额和工地任务关联，因此你必须构造模拟数据，不能仅凭 CSV 中的防火性能字段推算实际库存需求。

## 五、技术架构应该怎么选？

对于这个小型切片，我建议优先考虑与 QAntum 当前技术栈兼容的方案，而不是另起炉灶。

Team Leader Web UI

Next.js / React · 库存状态、任务清单、处理操作

业务逻辑层

库存需求计算、缺料判断、状态校验

数据层

第一版可使用版本化模拟数据；需要持久化时再接 Supabase

交付流水线

GitHub → CI 测试与检查 → Vercel 部署

### 主要技术取舍

| 技术问题 | 建议 | 原因 |
| --- | --- | --- |
| 前端 | Next.js + React + TypeScript | 与现有技术栈一致 |
| 后端 | 先用 Next.js 服务端逻辑；按需扩展 Node.js API | 避免小项目过度设计 |
| 数据库 | 视第一版需要决定；需要持久化时用 Supabase | 不必为了展示数据库而增加复杂度 |
| 身份验证 | Demo 可暂不实现，但必须说明生产环境的访问控制要求 | 控制工作量，避免把公开 Demo 误当成生产系统 |
| 离线支持 | 第一版可以不实现 | 负责人工作台主要是开工前规划；需确认实际现场场景后再决定 |
| CI/CD | GitHub Actions + Vercel | 自动执行测试和部署 |

如果采用静态模拟数据，必须说明它只证明了前端和业务判断逻辑，并未验证真实库存集成、并发更新、数据权限等生产问题。

如果第一版支持用户提交处理决定，那么还要明确这些决定是只存在浏览器中、保存在数据库中，还是写入真实业务系统。三者的承诺完全不同。

## 六、测试部分究竟考察什么？

Senior 工程师不只是证明正常情况可以运行，还要证明关键错误不会悄悄发生。

建议至少考虑以下测试：

| 测试类型 | 示例 |
| --- | --- |
| 单元测试 | 需求 24、库存 10，短缺是否正确算出 14 |
| 边界测试 | 需求恰好等于库存时，状态是否为充足 |
| 缺失数据测试 | 库存未知时，是否错误显示为充足 |
| 业务规则测试 | 未批准的替代方案是否会被错误认定为合规 |
| UI / 集成测试 | 用户是否能查看短缺并记录处理决定 |
| 失败场景测试 | 数据加载失败时，页面是否给出清晰提示 |
| CI 验证 | 测试失败时，流水线是否阻止部署 |

另外还需要说明测试的边界。比如，如果数据全是模拟的，你不能声称已经验证了真实 Supabase 权限、供应商 API 或离线同步。

## 七、AI Coding Agent 的使用是一个独立的考察重点

我认为这部分很重要。题目不是简单地问“你会不会使用 AI 写代码”，而是要求你展示一个可验证的开发过程。

建议你在仓库中保存如下记录：

`docs/spec.md`

功能需求、验收标准、业务规则和明确排除项。

`docs/architecture.md`

架构图、数据模型、接口、关键决策与技术取舍。

`docs/test-strategy.md`

风险、测试范围、失败场景和 CI 中运行的测试。

`AGENTS.md` 或对应的 Agent 指令文件

项目结构、编码规范、业务约束、测试要求，以及 Agent 不允许擅自改变的决策。

Agent 使用与审查记录

记录 Agent 的建议、你发现的问题、拒绝或修正的原因，以及最终验证证据。

举个很有价值的面试案例：

> Agent 建议在找不到库存记录时，把库存默认设置为 0。这样代码虽然可以继续计算，但会把“库存未知”错误地当成“确认没有库存”。我拒绝了这个建议，将库存状态改为 Unknown，并增加测试，确保系统不会给出错误的开工结论。

这类例子能够同时体现业务理解、代码审查、风险意识和 AI 使用能力。

实际面试时，最好展示真实发生的 Agent 修正案例，而不是为了满足题目而编造开发记录。

## 八、面试官最终如何判断你是不是 Senior？

业务判断正确

你解决的是施工负责人真实的问题，而不是为了展示技术而开发功能。

范围控制得当

第一版小而完整，有清楚的边界和合理的后续迭代。

技术决策有依据

能解释为什么这样设计，也能解释哪些功能暂时不做。

工程交付完整

应用可访问、测试真实运行、CI/CD 可检查、部署可验证。

真正掌握 Agent 生成的代码

能指出 Agent 的错误、说明自己的修正，并现场追踪代码执行过程。

## 我的结论

这道题不是传统的算法题，也不是单纯的全栈开发题。它更接近一次小型的、以 AI 为辅助工具的软件交付演练。

对于有企业级开发经验的 Senior 候选人，最容易拉开差距的不是多写几个页面，而是以下三个方面：

1. 选择正确的问题： 让 Team Leader 更早发现材料短缺，并知道下一步该做什么。
2. 建立可靠的工程闭环： 从需求、设计、实现到测试、部署，每一步都能验证。
3. 证明你驾驭 AI，而不是依赖 AI： Agent 可以写代码，但业务判断、架构决策和最终质量责任始终属于你。

如果只能优先投入精力，我会把重点放在：一个真正有用的 first slice、清晰的规格与架构、关键业务规则的测试，以及面试时能讲清楚的真实 Agent 审查案例。 这比做一个功能很多、但未经验证的 Demo 更符合题目强调的 Senior 工程能力。
